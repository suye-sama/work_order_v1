================================================================================
        轻量化售后工单系统 — 开发流程（个人学习版）
        聚焦 Agent 核心能力，非 Agent 部分简易开发
================================================================================

技术栈：FastAPI + Flask Agent + LangChain + LangGraph + Vue3 + PostgreSQL + Chroma
开发环境：Windows 本地，Python 3.11 (conda: work_order)，Node.js 20


================================================================================
第一阶段：基础骨架搭建（非 Agent 部分，简易开发）
================================================================================

目标：让系统"能跑通"，提供 Agent 所需的基础数据和展示页面。
原则：最小化、够用就行，不追求完善。

1.2 FastAPI 基础 CRUD（简易版）
----------------------------------------------------------------

  提供最精简的 REST API，用于前端调通流程：

  ┌─────────────────────────────────────────────────┐
  │ 接口              │ 方法   │ 说明               │
  ├───────────────────┼────────┼────────────────────┤
  │ /api/v1/auth/login│ POST   │ 简易用户名密码登录  │
  │ /api/v1/auth/me   │ GET    │ 获取当前用户        │
  │ /api/v1/tickets   │ GET    │ 工单列表（分页筛选）│
  │ /api/v1/tickets   │ POST   │ 创建工单            │
  │ /api/v1/tickets/{id}│ GET  │ 工单详情 + 时间线   │
  │ /api/v1/tickets/{id}│ PUT  │ 编辑工单            │
  │ /api/v1/tickets/{id}/status│ POST │ 状态流转     │
  │ /api/v1/customers │ GET    │ 客户列表            │
  │ /api/v1/customers │ POST   │ 新增客户            │
  │ /api/v1/dashboard/todo│ GET│ 我的待办            │
  │ /api/v1/dashboard/doing│ GET│我的进行中           │
  └─────────────────────────────────────────────────┘

  实现方式：
  - backend/app/api/auth.py        认证路由
  - backend/app/api/tickets.py     工单路由
  - backend/app/api/customers.py   客户路由
  - backend/app/api/dashboard.py   工作台路由
  - backend/app/services/          业务逻辑层
  - backend/app/schemas/           Pydantic 请求/响应模型

  简化策略：
  - 不做钉钉 OAuth，用简单的 username/password + JWT
  - 不做 RBAC 细粒度权限，只区分 admin / engineer 两种角色
  - 不做 WebSocket，用轮询替代
  - 不做消息推送模块
  - 不做报表中心和 Excel 导出
  - 状态机简化：新建 → 处理中 → 待确认 → 已完成 → 已归档

  │  │              (条件路由)                    │   │
  │  └──────────────────────────────────────────┘   │

2.2 Agent 1：售后过程采集 Agent（process_recorder）
----------------------------------------------------------------

  核心目标 1：自动记录售后过程

  功能：接收工程师的终端日志/操作记录，解析为结构化时间线。

  ┌────────────────────────────────────────────────────────┐
  │  输入：原始日志文本（SSH日志/堡垒机会话/粘贴文本）      │
  └─────────────────────┬──────────────────────────────────┘
                        ▼
  ┌────────────────────────────────────────────────────────┐
  │  LangGraph 工作流 (parse_graph)                         │
  │                                                        │
  │  Node 1: 日志清洗                                      │
  │    - 去除 ANSI 转义序列、乱码                           │
  │    - 统一 UTF-8 编码                                    │
  │    - 识别并标记时间戳                                   │
  │                                                        │
  │  Node 2: 命令识别（LLM 调用）                           │
  │    - 识别执行的命令 (systemctl, docker, kubectl...)     │
  │    - 识别命令输出中的错误信息                            │
  │    - 识别文件操作 (cat, vim, echo > ...)               │
  │                                                        │
  │  Node 3: 阶段分割                                      │
  │    - 按时间线将日志切分为若干阶段                        │
  │    - 每个阶段标记一个"操作意图"                          │
  │    例如: "登录环境" → "查看日志" → "定位问题" → "修复"  │
  │                                                        │
  │  Node 4: 摘要生成（LLM 调用）                           │
  │    - 对每个阶段生成一句话摘要                            │
  │    - 提取该阶段的关键发现                                │
  │    - 标记异常事件                                       │
  │                                                        │
  │  Node 5: 标准化输出                                    │
  │    - 组装为标准时间线 JSON                               │
  │    - 存入 ticket_timeline 表                            │
  └─────────────────────┬──────────────────────────────────┘
                        ▼
  ┌────────────────────────────────────────────────────────┐
  │  输出：结构化时间线 JSON                                 │
  │                                                        │
  │  [                                                     │
  │    {                                                   │
  │      "step": 1,                                        │
  │      "time": "2026-01-10 14:30:00",                    │
  │      "phase": "环境检查",                               │
  │      "operation": "SSH 登录",                           │
  │      "command": "ssh root@192.168.1.100",              │
  │      "summary": "通过堡垒机登录客户服务器",              │
  │      "result": "登录成功"                               │
  │    },                                                  │
  │    {                                                   │
  │      "step": 2,                                        │
  │      "time": "2026-01-10 14:32:15",                    │
  │      "phase": "故障定位",                               │
  │      "operation": "查看 Nginx 状态",                    │
  │      "command": "systemctl status nginx",              │
  │      "summary": "发现 Nginx 服务未运行",                │
  │      "result": "nginx.service: inactive (dead)"        │
  │    },                                                  │
  │    ...                                                 │
  │  ]                                                     │
  └────────────────────────────────────────────────────────┘

  LangGraph 关键技术点：
  - 使用 StateGraph 管理中间状态
  - 条件路由：如果日志超过 1000 行，先切分为多个片段并行处理
  - 使用 send() API 实现并行分片处理（Map-Reduce 模式）

2.3 Agent 2：工单自动生成 Agent（ticket_generator）★ 最核心
----------------------------------------------------------------

  核心目标 2：自动生成结构化工单 + 核心目标 3：智能总结故障信息

  功能：汇总所有售后数据，通过多阶段 Prompt Chain 生成标准工单。

  ┌────────────────────────────────────────────────────────┐
  │  输入：                                                  │
  │    - 工单基本信息 (title, customer, description)        │
  │    - 客户环境信息 (产品版本, 部署方式, OS)               │
  │    - 时间线数据 (Agent 1 的输出)                         │
  │    - 原始日志文本                                       │
  │    - 工程师备注                                         │
  └─────────────────────┬──────────────────────────────────┘
                        ▼
  ┌────────────────────────────────────────────────────────┐
  │  LangGraph 工作流 (generate_graph)  — 多阶段串行推理    │
  │                                                        │
  │  ┌──────────────────────────────────────────────┐      │
  │  │ Stage 1: 故障现象提取                          │      │
  │  │  Prompt: "阅读以下售后处理记录，提取故障现象..." │      │
  │  │  输出: { fault_phenomenon, impact_scope }     │      │
  │  └──────────────────┬───────────────────────────┘      │
  │                     ▼                                   │
  │  ┌──────────────────────────────────────────────┐      │
  │  │ Stage 2: 排查过程梳理                          │      │
  │  │  Prompt: "根据时间线和日志，梳理排查步骤..."    │      │
  │  │  输出: [{ step, action, finding }, ...]       │      │
  │  └──────────────────┬───────────────────────────┘      │
  │                     ▼                                   │
  │  ┌──────────────────────────────────────────────┐      │
  │  │ Stage 3: 根因分析                              │      │
  │  │  Prompt: "基于上述排查过程，分析故障根因..."    │      │
  │  │  输出: { root_cause, cause_detail }           │      │
  │  └──────────────────┬───────────────────────────┘      │
  │                     ▼                                   │
  │  ┌──────────────────────────────────────────────┐      │
  │  │ Stage 4: 解决方案总结                          │      │
  │  │  Prompt: "总结最终解决方案和后续建议..."        │      │
  │  │  输出: { solution, steps, suggestion }        │      │
  │  └──────────────────┬───────────────────────────┘      │
  │                     ▼                                   │
  │  ┌──────────────────────────────────────────────┐      │
  │  │ Stage 5: 工单摘要生成                          │      │
  │  │  Prompt: "用一段话概述整个售后处理过程..."      │      │
  │  │  输出: { summary, tags, duration_minutes }    │      │
  │  └──────────────────┬───────────────────────────┘      │
  │                     ▼                                   │
  │  ┌──────────────────────────────────────────────┐      │
  │  │ Stage 6: 结构化组装                            │      │
  │  │  将 5 个阶段的输出组装为完整工单 JSON           │      │
  │  │  使用 PydanticOutputParser 校验格式            │      │
  │  └──────────────────────────────────────────────┘      │
  └─────────────────────┬──────────────────────────────────┘
                        ▼
  ┌────────────────────────────────────────────────────────┐
  │  输出：标准化工单 JSON                                   │
  │                                                        │
  │  {                                                     │
  │    "fault_phenomenon": "用户无法登录系统，              │
  │                         浏览器显示502错误",            │
  │    "impact_scope": "全校教师无法使用教务系统",          │
  │    "troubleshooting": [                                │
  │      { "step": 1, "action": "检查Nginx状态",           │
  │        "finding": "Nginx服务未运行" },                 │
  │      { "step": 2, "action": "启动Nginx",               │
  │        "finding": "启动失败，端口被占用" },             │
  │      { "step": 3, "action": "查看端口占用",             │
  │        "finding": "旧进程残留占用80端口" }             │
  │    ],                                                  │
  │    "root_cause": "服务器重启后旧Nginx进程未正常退出，   │
  │                   占用80端口导致新进程无法启动",        │
  │    "solution": "1.kill残留进程 2.重启Nginx服务          │
  │                 3.配置systemd自动重启",                 │
  │    "summary": "本次故障为服务器重启导致的服务残留问题，  │
  │               通过清理残留进程并配置自动重启解决...",   │
  │    "tags": ["Nginx", "端口占用", "服务异常"],           │
  │    "duration_minutes": 45                              │
  │  }                                                     │
  └────────────────────────────────────────────────────────┘

  LangGraph 关键技术点：
  - 使用 StateGraph 串联 6 个 Node
  - 每个 Node 的输出通过 State 向下传递（共享上下文）
  - Stage 2 可以调用 Tool 查询历史相似工单，辅助排查过程整理
  - 使用 PydanticOutputParser 保证每个 Stage 输出格式正确

2.4 Agent 3：故障分析 Agent（fault_analyzer）
----------------------------------------------------------------

  核心目标 3 的深化：不只是总结文字，而是深度分析

  功能：对工单进行深度分析，输出版本级别的故障模式。

  LangGraph 工作流 (analyze_graph)：

  ┌────────────────────────────────────────────────────────┐
  │  Node 1: 相似故障检索                                    │
  │    - 将当前工单 Embedding → 在 Chroma 中检索相似工单      │
  │    - 返回 Top 5 相似案例                                 │
  │                                                        │
  │  Node 2: 对比分析（LLM 调用）                            │
  │    - 当前故障 vs 历史相似故障                            │
  │    - 识别是否为"已知问题"还是"新型故障"                   │
  │    - 分析故障复现条件                                    │
  │                                                        │
  │  Node 3: 风险评估                                       │
  │    - 评估故障严重程度                                    │
  │    - 判断是否可能再次发生                                │
  │    - 影响的产品版本范围                                  │
  │                                                        │
  │  Node 4: 改进建议                                       │
  │    - 短期修复方案                                       │
  │    - 长期优化建议                                       │
  │    - 预防措施                                           │
  └────────────────────────────────────────────────────────┘

  输出示例：
  {
    "fault_category": "服务异常",
    "is_known_issue": true,
    "similar_cases": ["TK-2025-089", "TK-2025-142"],
    "recurrence_risk": "中",
    "affected_versions": ["V3.2.0", "V3.2.1"],
    "severity": "高",
    "prevention": "建议在服务器重启脚本中加入 Nginx 健康检查"
  }

----------------------------------------------------------------
2.5 Agent 4：知识沉淀 Agent（knowledge_extractor）
----------------------------------------------------------------

  核心目标 4：自动沉淀知识资产

  功能：工单完成后，自动提取知识条目并向量化存储。

  LangGraph 工作流 (knowledge_graph)：

  ┌────────────────────────────────────────────────────────┐
  │  Node 1: 三元组提取（LLM 调用）                         │
  │    输入：完整工单                                        │
  │    输出：{ phenomenon, root_cause, solution }           │
  │                                                        │
  │  Node 2: 知识条目生成（LLM 调用）                        │
  │    将三元组扩充为标准知识条目：                            │
  │    { title, category, tags, summary, steps,             │
  │      applicable_versions, difficulty }                 │
  │                                                        │
  │  Node 3: Embedding 生成                                 │
  │    调用 Embedding 模型 (text-embedding-3-small / bge)    │
  │    生成知识条目的向量表示                                │
  │                                                        │
  │  Node 4: 向量存储                                       │
  │    将 Embedding + 元数据写入 Chroma                      │
  │    同时写入 PostgreSQL knowledge 表（二期）              │
  │                                                        │
  │  Node 5: 去重检查                                       │
  │    在 Chroma 中搜索相似向量                              │
  │    如果相似度 > 0.95，则视为重复知识，合并更新            │
  └────────────────────────────────────────────────────────┘

2.7 Agent 调用流程（端到端）
----------------------------------------------------------------

  完整的一次售后工单处理流程：

  用户操作                    FastAPI                    Agent
  ───────                    ──────                     ─────

  1. 创建工单 ─────────────▶ POST /tickets
                              (保存工单)

  2. 粘贴日志 ─────────────▶ POST /tickets/{id}/log ──▶ /agent/log/parse
     (在工单详情页                                      (日志 → 时间线)
      粘贴终端日志)          ◀── 返回时间线 ────────────

  3. 点击"AI生成"──────────▶ POST /tickets/{id}/ ────▶ /agent/ticket/generate
                              generate                   (时间线+日志+备注
                                                         → 完整工单)
                              ◀── 返回工单草稿 ──────────

  4. 工程师审核确认 ────────▶ PUT /tickets/{id}/status
     (修改+提交)              (待确认 → 已完成)

  5. 自动触发 ──────────────────────────────────────▶ /agent/knowledge/extract
     (工单完成后自动)                                   (知识提取+向量化)

----------------------------------------------------------------
3.1 FastAPI 调用 Agent 的集成方式
----------------------------------------------------------------

  同步模式（学习阶段推荐）：
    FastAPI 直接通过 httpx 调用 Flask Agent，等待返回结果。
    适用于单次 Agent 调用耗时在 10 秒以内的场景。

  异步模式（使用 Celery）：
    对于耗时较长的任务（如工单生成），FastAPI 创建 Celery 任务，
    前端轮询 /agent/ticket/generate/{task_id} 获取结果。

  推荐学习路径：先用同步模式调通，再改异步。

================================================================================
关键技术要点提醒
================================================================================

  1. LangGraph StateGraph 使用 TypedDict 定义状态结构，每个 Node 接收
     state 并返回部分更新，实现步骤间数据传递。

  2. LLM 调用是最大延迟来源，建议：
     - 学习阶段使用阿里百炼 Qwen-Plus API（国内访问快）
     - 或本地 Ollama 运行 qwen2.5:7b（免费但速度取决于显卡）
     - 在 agent/llm/factory.py 中统一管理，方便切换

  3. PydanticOutputParser 确保 LLM 输出结构可靠：
     - 每个 Agent 的输出定义 Pydantic Schema
     - LLM 输出格式不符合时自动重试（LangChain 内置机制）

  4. 学习阶段数据库可以全用 Docker 容器：
     - PostgreSQL → docker compose 中的 postgres 服务
     - Redis → docker compose 中的 redis 服务
     - Chroma → 先用 Python 包内置模式（无需单独启动服务）

  5. 前端开发时，Vite 的 proxy 配置（已在 vite.config.js 中配置）
     - /api → FastAPI 8000
     - /agent → Flask Agent 5000
     这样开发时无跨域问题。
